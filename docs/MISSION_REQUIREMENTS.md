## 0. 자료의 성격과 적용 범위

**출처 M**은 사용자가 이 대화에 붙여 넣은 코디세이 B7-1 미션 본문이다. 학습 플랫폼에 직접 접속해 최신 내용을 확인한 문서는 아니다. 아래 1~7절은 제공된 미션의 표현과 구성, 필수/선택 구분을 보존했다. 플랫폼의 빈 이미지 표식과 중복 화면 라벨만 생략했고 코드 예시의 fence 표기만 읽기 쉽게 정리했다.

새 구현 선택은 8절 이후와 `IMPLEMENTATION_SPEC.md`에서 분리한다. API 주소·인증 방식·구체 DB 스키마·8초·500자·AWS 특정 인스턴스가 모두 공식 미션이 강제한 사항인 것처럼 해석하지 않는다.

## 1. 미션 소개

기술이 조각나 있으면 서비스가 안 됩니다. 이번엔 합칩니다. 팀을 꾸리고, AI 챗봇 서비스를 기획부터 배포까지 직접 진행합니다. 리눅스, 웹, DB, AI API를 하나의 흐름으로 연결하는 경험, 그게 이 프로젝트의 목표입니다.

리눅스 환경 구성, 웹 개발, 데이터베이스 구축, AI API 연동 기술은 현대적인 웹 서비스를 만드는 핵심 요소입니다. 이 기술들은 개별적으로도 중요하지만, 하나의 서비스 안에서 유기적으로 통합될 때 비로소 완전한 가치를 발휘합니다.

이 미션에서는 팀 단위 협업을 통해 사용자 문의에 실시간으로 응답하는 AI 챗봇 서비스를 직접 기획하고 개발합니다. 메신저 플랫폼과 연동되거나 독자적인 웹 인터페이스를 가진 애플리케이션을 완성하며, 사용자 질문을 AI 모델에 전달하고 응답을 받아 출력하는 전체 파이프라인을 구축합니다.

이 과정을 통해 분산적으로 학습한 지식들이 실제 서비스에서 어떻게 상호작용하는지 깊이 있게 이해하고, 팀 단위 소프트웨어 개발 및 배포 실무 역량을 확보하게 됩니다.

## 2. 최종 결과물

다음 2가지 조건을 만족시키고, 정상 동작하는 웹 애플리케이션 1개를 완성한다.

1. **웹 기반 AI 챗봇 서비스 (FastAPI)**
   - 입력/요청: 사용자가 웹 페이지에서 텍스트 질문을 입력한다. (로그인 상태)
   - 처리: 서버가 질문을 수신하고 AI API를 호출해 응답을 생성한다.
   - 출력/화면: AI 응답이 웹 화면에 표시된다.
   - 접근성: 평가 시점에 외부 네트워크에서 접속 가능한 서비스 URL이 제공되어야 한다.
2. **프로젝트 산출물 (검증 가능 패키지)**
   - GitHub Repository 링크
   - README/기술 문서
     - 프로젝트 개요(문제 정의, 타겟 사용자, 핵심 시나리오)
     - 시스템 구조(간단 아키텍처, 주요 컴포넌트 역할)
     - API 명세(요청/응답 예시 포함)
     - DB 구조(ERD 또는 테이블/필드 설명)
     - 배포/실행 방법(환경 변수 설정 포함)
     - 팀 구성원 역할 및 개인별 작업 요약
     - 민감정보 관리(.env 예시 제공, .gitignore 적용 등)
   - DB 확인 가이드 (가능 범위 내, 아래 중 1개 이상)
     - 로그 조회 API 제공 및 예시 요청
     - 관리자/내부 로그 확인 화면 제공
     - 확인용 SQL 또는 스크립트 제공 (또는 캡처/증빙 자료 링크)

## 3. 과제 목표

이 과제를 마친 후, 학습자는 아래 내용을 스스로 설명할 수 있어야 한다.

- FastAPI로 웹 서비스(라우팅, 요청/응답, 템플릿 또는 프론트 연동)를 구성하는 흐름을 설명할 수 있다.
- 회원가입/로그인과 인증 상태에 따른 접근 제어를 서비스에 적용한 이유와 방식을 설명할 수 있다.
- “질문 수신 → AI API 호출 → 응답 반환 → 대화 로그 저장” 파이프라인을 설명할 수 있다.
- 대화 로그를 DB에 누적 저장하고 사용자 기준으로 조회/추적 가능하게 만든 설계를 설명할 수 있다.
- AI API 실패/타임아웃 상황에서 서비스가 비정상 종료되지 않도록 처리하고, 로그로 원인을 추적하는 방법을 설명할 수 있다.
- 브랜치 전략, PR 기반 협업, 문서화를 통해 팀 개발 품질을 유지하는 방법을 설명할 수 있다.

## 4. 기능 요구 사항

다음 요구사항을 모두 만족해야 한다.

### 4.1 웹 UI (질문 입력 인터페이스)

- 사용자가 질문을 입력할 수 있는 웹 페이지가 존재해야 한다.
- 질문 입력 후 응답이 같은 화면에서 확인 가능해야 한다. (형태 자유: 단일 페이지/페이지 전환 등)

### 4.2 사용자 인증 및 접근 제어

- 회원가입 및 로그인 기능이 정상 동작해야 한다.
- 인증 상태(로그인/비로그인)에 따라 접근 가능한 기능이 구분되어야 한다.
- “챗봇 질문/응답 기능”은 로그인한 사용자만 사용할 수 있어야 한다.

### 4.3 AI 챗봇 처리 (FastAPI 백엔드)

- 서버가 사용자 질문을 수신하고, AI API를 호출하여 응답을 생성해야 한다.
- AI API 호출은 서버에서 수행되어야 하며(키 노출 방지), 결과만 화면에 반환되어야 한다.
- 문맥 유지가 가능하도록, 최소한의 컨텍스트 구성 전략을 적용해야 한다.
  - 예: 최근 N개의 대화, 같은 사용자/세션의 직전 Q/A 등 (구현 방식은 팀이 선택)

### 4.4 대화 로그 저장 및 조회/추적

- 사용자 질문과 AI 응답이 DB에 누적 저장되어야 한다.
- 최소 추적 필드: 사용자 식별, 생성 시각, 질문, 응답
- “사용자 기준 로그 조회/추적”이 가능해야 한다.
  - 예: 내 로그 조회 API/화면, 관리자 조회 API/화면, 또는 확인용 쿼리/스크립트 제공(형태 자유)

### 4.5 운영 및 유지보수 (로그/예외/입력 검증)

- 서버 로그에 최소한 아래 이벤트가 남아야 한다.
  - 요청 수신 / AI 호출 / AI 응답 수신(또는 실패) / DB 저장 성공·실패
- AI API 실패/타임아웃 상황에서 서비스가 비정상 종료되지 않아야 한다.
- 사용자에게 오류가 발생했음을 알리는 응답(메시지/상태코드/안내)이 제공되어야 한다.
- 사용자 입력 검증 로직이 최소 1개 이상 존재해야 한다.
  - 예: 빈 입력 차단, 길이 제한 등

### 4.6 배포 및 접근성

- 배포된 서비스는 평가 시점 기준 외부 네트워크에서 접속 가능해야 한다.
- 배포/실행 방법과 환경 변수 설정 방법이 문서에 포함되어야 한다.

### 4.7 협업 및 형상관리

- 브랜치 전략이 적용되어야 한다. (예: main/develop 분리 또는 이에 준하는 운영)
- 기능 단위 작업 브랜치(또는 이에 준하는 작업 흐름) 흔적이 있어야 한다.
- PR 기반 Merge 기록이 존재해야 한다.
- 팀원별 유의미한 커밋이 10회 이상 존재해야 한다.
- 문서에 팀 역할/개인별 작업 요약이 포함되어야 하며, Git 이력과 크게 모순되지 않아야 한다.

## 5. 개발 환경

- Python & FastAPI로 구현한다.
- SQLite 사용을 권장하며, 평가자가 확인 가능한 형태로 연결/조회가 가능해야 한다.

## 6. 제약 사항

### 민감정보 및 설정 관리

- API 키, DB 비밀번호 등 민감정보를 코드/문서에 직접 작성하지 않는다.
- 모든 민감정보는 환경 변수(.env 등)로 관리한다.
- .env 파일은 저장소에 업로드되지 않도록 .gitignore를 적용한다.
- README에 환경 변수 키 목록(이름 수준)과 설정 방법을 포함한다.

### 운영 안정성

- AI API 호출은 타임아웃을 설정해야 하며(값은 팀이 선택), 실패 시 사용자에게 오류 안내를 반환해야 한다.
- 요청 수신, AI 호출/응답, DB 저장 성공·실패가 로그로 남아야 한다.

### 협업 규칙

- PR 기반으로 머지하고, 브랜치/PR 기록이 저장소에 남아야 한다.
- 팀원별 유의미한 커밋 최소 10회 이상 기록되어야 한다.
- 기술 문서에 팀 구성원 역할 및 개인별 작업 요약을 반드시 포함해야 한다.

## 9. 공식 최소조건과 팀 추가 결정의 구분

공식 미션은 Python/FastAPI, 인증, 실제 AI, 최소 문맥, DB, 로그/실패 처리, 외부 접속, 문서, 협업을 필수로 요구한다. SQLite는 공식 문구상 권장이지만 이번 팀은 선택했다. JWT/HS256/bcrypt, 8초, 500자, 5쌍, username, localStorage, EC2/2GB Swap 등은 **최신 첨부 팀 규칙과 계약**에 의해 이 구현에서 준수한다.

공식 120시간은 학습시간이고 팀 기획의 4일은 프로토타입 목표다. 이전 AGENTS의 10일 설명은 이번 최신 첨부에 의해 교체한다. 본 패키지가 4일 완성이나 평가 합격을 보장하지 않는다.

`check_logs.sql`은 공식 예시와 일치하는 **DB 대화 기록 조회용**이다. Python 운영 로그를 SQL로 검사한다고 설명하지 않는다. ‘4대 이벤트’는 요청/AI 호출/AI 결과/DB 결과의 네 범주이고 성공·실패를 나누면 6개 이벤트명이 될 수 있다.

## 10. 개발 시작 전에 먼저 만들 최소 증빙 틀

앱 코드를 대량 생성하기 전에 다음 기반을 R01에서 만든다.

- 본인 Git author·기능 브랜치·원격 목적지 확인. 실제 작업 단위별 커밋 계획을 먼저 기록.
- `.gitignore`와 비밀값 없는 `.env.example`, 최신 API/스키마 복원, PR/Issue 템플릿.
- README 초안: 미완성 상태, 문제·타겟·시나리오, 팀 예정 역할, 실제 구현자 구분.
- `docs/IMPLEMENTATION_STATUS.md`: 위 M01~M21 모두 최초 NOT_RUN으로 생성.
- `docs/CONTRIBUTIONS.md`: 실제 본인 작성자 정보, 작업·SHA·PR·검증·미반영 여부 칸.

이는 준비 단계다. 체크리스트 파일이 있다고 협업·배포·AI 조건을 통과한 것이 아니다.

## 11. 이번에 먼저 만들 ‘미션 최소 완성본’

단순 로그인/가입 모달, 질문창, 답변 영역, 로그아웃, 내 기록 재조회면 충분하다. API 5개, users/chat_logs 2개 테이블, 최근 5쌍 문맥, 6개 운영 이벤트, 정상/장애 테스트를 먼저 완성한다. 별도 관리자 화면·ERD 이미지·RAG·공공데이터·스트리밍·페이지네이션·브랜드 디자인은 추가하지 않는다. DB 문서는 필드 표와 SQL로 충분하다.

Mock 기반 로컬 최소본이 통과하면 실제 AI 및 외부 배포를 진행할 준비를 마친다. 승인/키/계정이 없으면 정확한 대기 항목을 남긴다. **실제 AI·외부 URL·팀원 각각의 10커밋·PR 조건은 생략 가능한 고도화가 아니다.**

## 12. 사람당 10커밋의 판정 경계

팀 4명 합계 40개는 필요 총량일 뿐 충분조건이 아니다. 한 명 37개·나머지 각 1개면 세 사람은 조건 미달이다. 한 명이 40개를 만들거나 다른 사람 이름으로 커밋하는 방법도 요건을 충족하지 않는다.

이 개인 저장소의 풀스택 20개는 본인 학습과 실험 기록이다. 나중에 팀 저장소에 프론트를 한 번 복사해 1개 커밋으로 올리면, 평가 기준에 따라서는 팀 저장소에서 확인되는 본인 작업이 1개에 그칠 수 있다. **현재 팀의 확정된 산정 범위는 첨부파일에 없다.** 따라서 보수적으로 평가 대상 저장소의 최종 제출 브랜치에 실제 개인 작업 커밋들이 포함되게 운영한다. 이는 명시적 운영 제안이지 미션 원문의 추가 문구가 아니다.

팀 PR은 원커밋을 보존하는 merge 방식을 합의하고, 병합 후 SHA와 작성자별 내용을 검사한다. squash가 강제되어 있으면 규칙을 일방 변경하지 말고 PR 증빙 인정범위 또는 작은 단일커밋 PR 흐름을 팀/퍼실리테이터와 확정한다. 자세한 절차와 4명 각각의 10개 작업 예시는 `MILESTONES.md`에 있다.

## 13. 최소 시연 및 개인 설명 카드

시연 순서: 가입 → 로그인 → 실제 AI 질문 → 직전 내용 재질문 → 내 기록 확인 → 로그아웃 → 미인증 차단 → 제한 입력 오류 → 테스트 환경에서 AI timeout/DB 실패 → 정상 복구 → 외부 네트워크에서 재확인. 정상 기록의 SQL 결과와 운영 이벤트는 실제 결과에서 민감정보를 제거해 제시한다.

개인 설명에는 다음 여섯 내용을 **자신이 실제 확인한 코드 경로**로 적는다: FastAPI 라우터와 화면 연결; 로그인 토큰이 필요한 이유; 질문/AI/저장/반환 순서; 사용자별 DB 격리; timeout과 로그 추적; 실제 브랜치·PR·커밋 운영. AI가 작성한 설명을 이해 여부 증거로 대신 제출하지 않는다.
