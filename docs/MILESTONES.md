# B7-1 마일스톤·최소 완성·개인별 커밋 운영

버전 2.0 / 검토 기준일 2026-09-16

## 1. 먼저 지킬 순서

공식 120시간과 팀의 4일 목표를 보존한다. 아래는 날짜가 지나야 진행하는 일정이 아니라 통과 기준이다. 첨부 계획의 담당 업무는 유지하지만 ‘Day3에 처음 결합’ 대신 **Day1 단계에서 인증·DB를 포함한 최소 Mock E2E**를 만든다. 실패·보안·입력 검증도 해당 기능 구현 때부터 넣는다.

가장 먼저 Git 작성자·브랜치·ignore·최신 API·증빙 틀을 준비한다. 그 뒤 화면을 꾸미기 전에 작동 경로를 뚫는다. 실제 AI·외부 접속·팀원 각10커밋·PR은 미션 필수조건이며 고도화로 뒤로 빼거나 삭제하지 않는다.

## 2. 시작 전 G0 — 미션 증빙 준비

확인할 것은 현재 작업 폴더, Git 상태/원격 주소, 사용자 본인의 author name/email, 최신 입력6개, 원자료11개다. 팀 Organization을 변경하는 작업인지 개인 reference 저장소인지 구분한다. 현재 전제는 후자다.

`.env.example`, `.gitignore`, API·스키마, PR·Issue 템플릿, README 초안, IMPLEMENTATION_STATUS/CONTRIBUTIONS의 빈 증빙 틀을 준비한다. ‘빈 틀 생성’과 ‘빈 파일을 만들어 커밋 숫자 채우기’는 다르다. 실제 근거·작업 계획·요구사항 추적 내용이 있어야 한다.

초기 상태값을 임의 PASS로 넣지 않는다. 본인 Git 정보가 없으면 사용자에게 필요한 설정을 알려주고 커밋은 대기로 둔다. 코드·테스트 가능한 부분은 진행해도 되지만 여러 단계를 완성한 뒤 과거에 한 것처럼 소급 커밋을 꾸미지 않는다.

R06~R15는 프론트 파일/해당 테스트·설명 중심으로 범위를 유지한다. 이를 위해 팀 백엔드 파일을 끼워넣는 대형 혼합 커밋을 피한다. 이것은 나중의 검토를 쉽게 하는 작업 분리일 뿐, **지금 프론트를 추출하거나 팀 저장소에 이식한다는 지시가 아니다.**

이미 R05가 서버 최소입력/오류를 처리하는데 R11/R12는 그 사용자 화면을 완성한다. 정상E2E를 통과시킨 뒤 오류테스트를 넣으려고 처음 기능을 일부러 결함 상태로 만들지 않는다. 각 단계에 필요한 기본 테스트는 즉시 포함한다.

### 각 단위에서 반복할 절차

현재 작업·수정파일 확인 → 한 기능 구현 → 관련 테스트 실제 실행 → diff와 민감파일 검사 → **정확한 파일만 stage** → 실제 본인 author로 commit → SHA/검증 결과 기록. 테스트가 실패하면 수정하고 같은 기능을 완성한다. 일부 테스트만 실행했으면 그렇게 적는다.

`git add .`를 습관적으로 사용하지 않는다. 패키지 원문 보존 블록의 원래 Markdown 끝공백과 새 코드의 실수는 구분하며 원문 해시를 훼손해 공백 검사를 통과시키지 않는다. `git diff --check`의 결과가 있으면 대상과 이유를 검토한다.

## 4. 4단계 최소 완성 게이트

### Day1 단계 — G1: 첫 수직 연결

R01~R09를 중심으로 실제 가입 → 로그인 → 보호 chat → Mock → SQLite → 화면 표시를 완주한다. 서버 단독 응답이나 브라우저 가짜fetch만으로 G1 PASS를 만들지 않는다. API필드·상태·기록·수신/AI/DB로그를 확인한다.

G1 통과: /health,가입201,로그인200,토큰없는chat401,유효토큰Mock200,DB한행,브라우저메시지. 브라우저도구가 없으면 HTTP 검증만PASS이며 브라우저NOT_RUN은 남긴다.

### Day2 단계 — G2: 미션 필수 로컬 기능

R10~R16을 진행한다. 기록복원·현재사용자문맥·실제AI adapter·모드·입력오류·토큰·로딩·반응형을 완성한다. 실제AI 정보와배포계정·비용승인은Day1부터 확인 대기로 기록해 마지막날 처음 발견하지 않는다.

G2 통과 조건은 내 기록 배열과 사용자 격리, 최근 5쌍 문맥, 원래 API 계약, 실제 HTTP 코드의 transport 테스트, UI 오류 복구다. 외부 키나 권한이 없다면 실제 AI 실행만 BLOCKED_EXTERNAL로 남긴다.

### Day3 단계 — G3: 실패 처리·미션 패키지

R17~R18을 중심으로 timeout·공급자실패·DB실패·운영로그·보존/격리·보안·확인도구를 검증한다. 문서와 실제API가 일치해야 한다. API가 다르다고 자기 프론트에 맞춰 일방 변경하지 않는다.

G3 통과: T01~T24·T29 등 로컬 자동 검증, 가능한 브라우저T25~T28, DB/로그검사. 실제 수행하지 않은 테스트는NOT_RUN. 모든로컬기능이완성되면 `LOCAL_MINIMUM` 보고를 먼저 남긴다. 아직 실제AI/URL/팀커밋이대기면 ‘미션전체완료’는 아니다.

### Day4 단계 — G4: 재현·외부 시연·팀 기록

R19~R20, T30~T33을 진행한다. 의존성 새 설치, 실행 명령, EC2 설정, DB 확인, 개인 설명, PR 초안과 상태표를 완성한다. 승인된 계정과 실제 키가 있을 때 외부에서 두 턴의 실제 AI 대화를 확인한다. 템플릿이 아닌 실제 서비스 URL과 확인 시각을 기록한다.

## 6. Git 운영 방법 — 개인과 팀을 분리

### 6.1 개인 reference 저장소

본인 로컬 작업 브랜치는 `feat/fullstack-lee`다. 팀 작업용 `feat/ui-lee`에 전체 백엔드를 섞어 넣지 않는다. 기존 Git 저장소가 있으면 원격과 기반을 확인하고, 없다면 승인된 현재 폴더에서 초기화한다.

빈 저장소의 최초 기준 커밋으로 문서, ignore, 설정 틀을 기록하고 필요하면 그 커밋에서 로컬 main/develop 참조를 만든다. 이는 최초 초기화일 뿐 PR merge를 한 것으로 기록하지 않는다. main에 완성 기능을 직접 커밋하거나 기존 원격을 수정하지 않는다.

본인 작성자 확인 명령:

```bash
git status --short --branch
git remote -v
git config --get user.name
git config --get user.email
```

공용 컴퓨터에서는 본인 정보를 저장소의 로컬 설정에만 사용한다. 이름·이메일이 없거나 다른 사람 값이면 그대로 커밋하지 않는다. 이메일은 GitHub에 연결한 본인 주소 또는 noreply를 확인해 설정하며 추측값을 넣지 않는다.

커밋 예시다. 파일은 실제 변경한 범위로 좁혀 선택한다.

```bash
git diff --check
git diff --stat
git add static/js/auth.js tests/test_frontend_contract.py
git diff --cached --stat
git commit -m "feat: 로그인 모달과 토큰 통신 구현"
```

실제 tests 파일이 그 단계에서 수정되지 않았다면 위 파일 목록을 그대로 복사하지 않는다. commit 생성은 사용자 승인과 정확한 author 아래에서 한다. 임의 --author, 빈 commit, 날짜 위장, 소급 분할은 하지 않는다.

### 6.2 평가 대상 팀 저장소

원래 팀 흐름은 feature → develop → main의 PR merge다. 개인 실험 저장소의 커밋은 팀 평가 증거로 자동 이동하지 않는다. 이식은 나중의 별도 작업이지만 그때 검증된 본인 변경만 팀 계약에 맞춰 올리고 실제 PR 기록을 남겨야 한다. 다른 팀원의 인증·AI 구현을 본인의 전체 구현으로 일방 대체하지 않는다.

본인 기여 10개를 최종 브랜치에서 확인하기 쉽도록 원커밋을 보존하는 merge를 권한다. Squash and merge는 여러 커밋을 한 개로 만들기 때문에 기준에 따라 집계 개수가 달라질 수 있다. 원문은 산정 알고리즘을 지정하지 않았으므로 ‘무조건 탈락’이라고 단정하지 않고 팀·퍼실리테이터와 범위를 확인한다. 승인 없이 보호 규칙을 변경하지 않는다.

PR 10개가 필수라는 뜻은 아니다. **필수는 유의미한 개인 커밋 10개와 실제 PR merge 이력**이다. PR은 기능과 리뷰 단위로 작게 만든다. 사전 계획이나 PR 템플릿만 있어서는 조건을 충족하지 못한다.

### 6.3 감사 명령과 실제 의미 검토

평가 대상 브랜치가 main인 경우 다음 명령은 작성자별 기본 수량을 확인하는 보조 수단이다. 원격 정보 최신화는 접속 권한과 승인 아래 수행한다.

```bash
git shortlog -sne --no-merges origin/main
git log --no-merges --format="%h %an <%ae> %s" origin/main
git log --oneline --graph --decorate --all
```

숫자만으로 PASS 처리하지 않는다. 기준 커밋이 있다면 `BASE_SHA..origin/main` 범위로 줄여 프로젝트 이전 작업을 제외한다. main 반영 전에는 develop에서 중간 확인하고 최종 제출 브랜치에서 재확인한다. author 이메일이 여러 개면 동일인임을 본인 확인 후 매핑하며 임의로 합치지 않는다.

`scripts/audit_contributions.py`의 최소 출력은 repository/ref/base, 실제 author 목록, non-merge SHA·제목·변경 파일, 후보 개수, 10개 미달 여부, 내용 검토 상태, PR 증거 유무다. 정확한 작성자 이메일이나 기준 범위가 없다면 NOT_RUN 또는 NEEDS_TEAM_REVIEW다. `--all`로 조회한 모든 실험 브랜치의 개수를 최종 반영 개수로 오인하지 않는다.

기여 기록 한 행은 `작성자 | 작업 | SHA | 검증 명령·결과 | PR URL | 대상 브랜치 반영 | 직접 설명 여부`로 작성한다. 새 기록을 넣는 커밋 자신의 SHA를 같은 커밋 안에 적으려 하지 말고, 최종 Git 이력에서 생성해 증빙한다.

## 7. 중단·재개·마무리

문제가 발생하면 API 경로 → method → JSON key → Content-Type → Bearer → status → 응답 필드 → DB·운영 로그 순서로 대조한다. 최신 api_spec를 자기 프론트에 맞게 몰래 바꾸지 않는다.

재개할 때는 현재 branch, SHA, working tree와 IMPLEMENTATION_STATUS를 먼저 읽고 다음 미완료 R 번호부터 진행한다. 한 단계가 실제로 합쳐진 경우 기록을 정직하게 남기고 빈 커밋으로 20개를 복구하지 않는다.

최종 보고는 로컬 필수 기능, 실제 AI, 공개 URL, 팀 이력의 네 줄 요약과 실제 테스트 결과를 포함한다. 본인 커밋 목록, 타인 기여 미확인, 외부 입력·승인 대기, 팀 합의가 필요한 C 항목도 적는다. 미션 필수 항목이 막혀 있다면 새 기능 추가보다 해결 조건을 먼저 명시한다.
